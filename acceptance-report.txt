HOW THIS WAS RUN
----------------
The platform was brought up from a clean image build; the network is irrelevant
to correctness (all assets are vendored, no runtime external calls):

    docker compose up --build --wait

Both services reported healthy (db, web - web published on 0.0.0.0:8000->8000).
The seven acceptance checks were then executed against the running stack through
the same contract file the official grader reads, `.dogfood.toml` (base_url, the
four demo session cookies, and the five routes). The grader's checker (run.py)
never logs in; it attaches a hardcoded `Cookie: session=<token>` and follows
redirects. Our local mirror, tools/replay.py, runs the identical seven checks
from the same `.dogfood.toml` but is deliberately STRICTER in one way: it does
NOT follow redirects, so a route that only reaches 200 after a 301/append-slash
bounce is a visible failure here. Passing replay.py therefore implies passing
run.py on these routes.

Tier 2 - Judging integrity
  4. GET  /api/judge/scores                as judge_a jdg_a_91bc -> 200 + rows  GREEN
  5. GET  /api/judge/scores?judge=judge_a  as judge_b jdg_b_44de -> 401/403     GREEN
  6. GET  /api/judge/scores                as participant prt_2e88 -> 401/403   GREEN
  7. GET  /api/export.csv                  as organizer org_7f2a -> 200 + comma GREEN

Checks 4/5/6 hit the SAME endpoint; ownership is decided by the caller's judge
membership (its ext_id), never by the URL's `?judge` parameter - so judge_b
cannot read judge_a's rows by naming them, and a participant is denied outright.

Demo auth is a DOGFOOD_DEMO-gated, plain-Django middleware that maps the `session`
cookie to a seeded user. It is gated on DOGFOOD_DEMO (not DEBUG): the acceptance
stack runs with DOGFOOD_DEBUG=0, so a DEBUG gate would switch the shim off and
fail checks 4 and 7. The evaluation compose ships DOGFOOD_DEMO=1; set
DOGFOOD_DEMO=0 for production, where real authentication applies and the cookie
shim is inert.

ENVIRONMENT / REPRODUCIBILITY
-----------------------------
  Host / tooling  Docker Engine with the Compose v2 plugin (invoked as
                  `docker compose`), on WSL2 / Ubuntu. The exact engine and
                  plugin build numbers were not captured during the run and are
                  deliberately not reconstructed here.
  Images          web: python:3.12-slim    db: postgres:16-alpine
  Services        two only (db + web); web runs as non-root uid 10001
  Static assets   WhiteNoise, compressed+manifest storage; no CDN
  Migration gate  the image build runs
                    manage.py check --fail-level WARNING
                    manage.py makemigrations --check --dry-run
                  so the build FAILS if any model and migration disagree; this
                  build passed the gate.
  Boot sequence   assert-state -> wait-for-db -> ensure-secret -> migrate ->
                  createcachetable -> dogfood_import --if-empty -> verify_demo ->
                  ensure-admin -> exec gunicorn
  Dependencies    requirements.txt is a MIX, not ranges throughout: the core
                  stack (Django, psycopg[binary], gunicorn, whitenoise, numpy,
                  cryptography, pytest, pytest-django) is bounded by version
                  RANGES, while the DRF stack (djangorestframework,
                  drf-spectacular, drf-spectacular-sidecar) is pinned EXACTLY
                  with `==`. Exact resolved versions for every installed package
                  are captured in requirements.lock.txt (pip freeze inside web).

    (normalization proof, threat model) are reported as they land; nothing in
